KV-Cache Inference

The generation loop earlier re-runs the whole context every step — correct but O(T²). A KV cache stores the keys and values of past tokens so each new step is O(T). This page is the working code: the cache, a cache-aware attention, and the two-phase prefill → decode loop, with a PyTorch proof that cached decoding is bit-for-bit identical to full recompute.

The idea in one paragraph

In attention, a token's K and V never change once computed — only the query is new each step. So cache all past K/V, and at each decode step compute just the new token's q, k, v, append k, v to the cache, and attend the single query over the whole cache. The concept and the cache-size formula are on Attention §5; here is the code.

1. Prefill vs decode

Generation has two phases with very different compute profiles:

PhaseInputWorkBound by
Prefillthe whole prompt (T tokens) at oncefill the cache; parallel over Tcompute (one big matmul)
Decodeone token at a timeappend 1 K/V, attend over cachememory bandwidth (read the cache)

This split is why serving systems report prefill and decode throughput separately, and why the KV cache (a memory-bandwidth problem) dominates decode latency and cost — the motivation for GQA/MLA and paged attention below.

2. The cache

Preallocate K/V tensors of shape (batch, n_kv_head, max_seq, head_dim) and track how many positions are filled. Preallocation avoids re-allocating every step (which would kill decode throughput).

3. Cache-aware attention

Project the incoming tokens, apply RoPE at their absolute positions (start_pos), append the new k, v to the cache, then attend. The one subtlety is the causal mask: during prefill the query and key lengths match, so is_causal=True; during decode the single query legitimately sees the entire cache (all past), so no mask.

⚠️ Three things that silently break KV caches

(1) RoPE position — apply it at the token's absolute position, not 0, or decoded tokens get the wrong rotation. (2) Chunked prefill — if you prefill in chunks (T>1 with a non-empty cache), is_causal=True is wrong; you need an explicit mask offset by cache.length − T. (3) Overflow — decoding past max_seq writes out of bounds; real caches evict (sliding window) or grow.

4. The generate loop: prefill then decode

Allocate one cache per layer, run the prompt once (prefill), then feed the model a single token at a time (decode). The model threads caches and start_pos into each layer's CachedAttention.

The model's forward(idx, caches, start_pos) is the RoPE model with each block taking (x, cache, cos, sin, start_pos) and passing them to CachedAttention. During decode idx is shape (B, 1), so every matmul is tiny — the cost is dominated by reading the growing cache.

5. Verify it's identical to full recompute

A KV cache is an optimization: cached decoding must produce exactly what recomputing the full prefix would. This cell proves it for single-head attention — process tokens one at a time with a cache, and compare each step's output to recomputing attention over the whole prefix from scratch.

6. Memory, and why paging exists

        

          The cache is often the memory bottleneck at serving time. Its size (revisit the formula on
          Attention §5):
        

        

          bytes = 2 (K,V) × n_layer × n_kv_head × head_dim × seq × batch × dtype_bytes
        

        
    
          
  • GQA / MLA shrink the n_kv_head (or the cached latent) term —
            the single biggest lever on cache size (Newer Architectures).
    • 
          
  • Paged attention (vLLM) — instead of one contiguous
            max_seq buffer per sequence (which wastes memory on padding and fragments), store
            the cache in fixed-size blocks and keep a per-sequence block table, like OS virtual
            memory. This lets many sequences of varying length share the pool with almost no waste and
            enables prefix sharing.
    • 
          
  • Sliding-window cache — for windowed attention, keep only the last
            window positions and overwrite in a ring buffer, bounding the cache regardless of
            sequence length.
    • 
        


        

          
Why this matters

          

            Likely probes: "Why is decode memory-bound?" → each step reads the entire cache but does tiny
            matmuls, so arithmetic intensity is low (roofline). "How do you
            fit more concurrent users?" → shrink the cache (GQA/MLA), page it (vLLM), or quantize it.
            "What's the cost of a KV cache?" → recite the formula and note it scales with batch × context,
            which is why long-context serving is expensive.
