Topic 07 · Systems

Distributed Training & Parallelism

Scaling one training job to thousands of accelerators is where LLM engineering gets real. The bar: given a model and a cluster, propose a parallelism strategy and defend it with memory math, collective costs, and MFU — not vibes. The runnable cells here are calculators you should be able to reproduce on a whiteboard.

1. Why we shard at all: the memory wall

Start every distributed discussion from memory. Training with mixed-precision Adam costs roughly 16 bytes per parameter for model states alone, before a single activation:

fp16 params (2) + fp16 grads (2) + fp32 master params (4) + fp32 Adam m (4) + fp32 Adam v (4) = 16 bytes / param

That's the number the ZeRO paper is built around. A 7B model needs ~112 GB of state — it does not fit on an 80 GB GPU, and that's before activations. Sharding is not an optimization; it's a requirement.

2. The parallelism taxonomy


        
Data parallelism (DP)

        

          Replicate the full model on each device, split the batch across devices, and
          all-reduce gradients before the optimizer step. Simple and
          communication-efficient (one all-reduce per step), but every device holds a full copy —
          so it does nothing for the memory wall. It's the outermost layer of almost every real
          setup.
        


        
ZeRO / FSDP — sharded data parallelism

        

          The key insight of ZeRO (and PyTorch's FSDP): in plain DP the optimizer states, gradients,
          and params are redundantly replicated. Shard them across the DP group instead, and
          gather just-in-time. Three stages, increasing memory savings for increasing communication:
        

        

          

            
StageShardsMemory / device (Ψ = params)Extra comm vs DP

            
              
Baseline DPnothing16Ψ—

              
ZeRO-1optimizer states4Ψ + 12Ψ/Nnone (same all-reduce)

              
ZeRO-2+ gradients2Ψ + 14Ψ/Nnone (reduce-scatter)

              
ZeRO-3 / FSDP+ parameters16Ψ/N~1.5× (all-gather params fwd & bwd)

            
          

        

        

          FSDP is ZeRO-3's design: params live sharded, are all-gathered per layer just before it
          runs, then freed. This is why ZeRO-3 turns an all-reduce into an all-gather (forward) +
          reduce-scatter (backward) — an all-reduce is those two, so the total volume is
          ~1.5× DP, and it lets memory scale down with N.
        


        

          

            ZeRO memory per device
            
            
            
          

          
          

        


        
Tensor parallelism (TP)

        

          Split individual layers across devices. In a transformer, the MLP's two matmuls
          and attention's heads shard cleanly (Megatron-LM): the first weight matrix is split
          column-wise, the second row-wise, so only two all-reduces per layer
          (forward + backward) are needed. TP shards params, grads, optimizer state, and
          activations — but it demands very high interconnect bandwidth (each layer synchronizes), so
          it's kept within a node (NVLink), typically TP=8.
        


        
Pipeline parallelism (PP)

        

          Split the model by layers into stages, each on a different device; activations
          flow forward stage-to-stage, gradients backward. The problem is the bubble:
          while stage 1 processes micro-batch 1, stages 2–p sit idle. Splitting the batch into
          m micro-batches (GPipe) and interleaving (1F1B) shrinks the bubble.
        

        

          bubble fraction ≈ (p − 1) / (m + p − 1)   →   large m amortizes the idle time.
        


        

          

            Pipeline bubble
            
            
            
          

          
          

        


        
Sequence / context parallelism (SP/CP)

        

          Long context makes activations the bottleneck (they scale with sequence length).
          Sequence parallelism shards the sequence dimension across devices — for the parts of the
          layer that are elementwise along the sequence (norms, dropout, the residual) — and combines
          with TP. Context parallelism (e.g. ring attention) shards the sequence through attention
          itself, exchanging K/V blocks between devices. This is what enables 100k+ token training.
        


        
Expert parallelism (EP)

        

          For MoE models, place different experts on different devices; tokens are routed with an
          all-to-all to their expert's device and back. EP composes with the others
          and is why MoE scales — only the active experts' params participate per token.
        


        

          
In practice — "3D parallelism"

          

            Real frontier runs compose these: e.g. TP=8 within a node (NVLink),
            PP across a few nodes, DP/FSDP across the rest. The ordering
            matters — put the highest-bandwidth-demand parallelism (TP) on the fastest links, the
            lowest (DP) on the slowest. Be ready to sketch this mapping for a given cluster topology.
          

        


        
        
3. Collectives — the primitives underneath

        

          Every strategy above is built from a handful of collective operations. Know what each does
          and its cost:
        

        

          

            
CollectiveEffectUsed by

            
              
all-reduceevery device ends with the sum of all inputsDP gradient sync

              
reduce-scattersum, then each device keeps one shardZeRO-2/3 backward

              
all-gathereach device collects all shardsZeRO-3/FSDP forward

              
broadcastone device's data copied to allinit, checkpoints

              
all-to-alleach device sends a distinct chunk to each otherMoE expert routing

            
          

        

        

          The identity to remember: all-reduce = reduce-scatter + all-gather. A
          ring all-reduce moves ~2(N−1)/N × data bytes per device and is
          bandwidth-optimal — critically, its cost is independent of N in the limit
          (approaches 2×data), which is why DP scales. Tree algorithms trade bandwidth for lower
          latency on small messages.

4. Activations & recomputation

        

          Activations stored for the backward pass often dominate memory at large batch/seq.
          Activation checkpointing (a.k.a. gradient checkpointing / recomputation)
          stores only layer boundaries and recomputes the intermediate activations during backward —
          trading roughly one extra forward pass (~33% more compute) for a large
          memory reduction. It's the standard knob when you're activation-bound.

5. Measuring efficiency: MFU

        

          Model FLOPs Utilization is the headline efficiency metric: the fraction of
          peak hardware FLOP/s your run actually uses for useful model math. Training a dense
          transformer costs ~6N FLOPs per token (N = params: 2 for forward, 4 for
          backward). Good large-scale runs land around 40–55% MFU; below ~30% something is wrong
          (comm-bound, bad overlap, small batch).
        

        

          MFU = (6 × N × tokens_per_second) / (num_devices × peak_FLOP/s_per_device)

⚠️ MFU vs HFU

          

            Hardware FLOPs Utilization counts all FLOPs executed, including
            the recomputation from activation checkpointing; Model FLOPs Utilization
            counts only the useful 6N and ignores recompute. So enabling checkpointing
            raises HFU but slightly lowers MFU (you did extra work). Quote MFU for
            "how good is my run"; know the distinction if pressed.
          

        


        
        
6. Putting it together — the design question

        

          The capstone question of this whole topic is "here's a model and a cluster — how do you train it?"
          A structured answer:
        

        
    
          
  1. Memory first: compute model-state GB (16Ψ) and activation GB. Does one
            device hold it? If not, how much sharding is forced?
    2. 
          
  2. Pick the axes: TP within a node (≤8, on NVLink); PP across a few nodes
            if the model is too deep for TP alone; FSDP/DP across the remainder. Add SP/CP for long
            context, EP for MoE.
    3. 
          
  3. Check comm: estimate the all-reduce/all-gather time vs compute time per
            step — is the collective hidden behind compute (overlap) or exposed?
    4. 
          
  4. Tune the batch: global batch = micro-batch × grad-accum × DP-degree;
            large enough for good MFU and to amortize the pipeline bubble, small enough to stay near
            the critical batch size (see Training Dynamics).
    5. 
          
  5. Measure MFU, find the bottleneck, iterate.
    6. 
        


        

          

            Exercise
            Plan a 70B run on 256 H100s
            
          

          

            Using the calculators above: a 70B dense model, 256 H100 (80 GB, ~990 bf16 TFLOP/s peak),
            8k context. Propose TP/PP/DP degrees so it fits in memory, estimate per-step all-reduce
            time, choose micro-batches to keep the pipeline bubble under 10%, and state a target
            tokens/sec for 45% MFU. Write down every number and its formula.
          

          

            Approach sketch
            

              Model states 16×70B = 1120 GB → needs sharding across ≥14 GPUs minimum just for states.
              A common layout: TP=8 (intra-node), PP=4, DP=8 (=256). With TP+PP the per-device param
              shard is 70B/(8×4)=2.2B → ~35 GB states, leaving room for activations (use checkpointing
              at 8k seq). For PP=4 keep m≥16 micro-batches → bubble = 3/(16+3) ≈ 16%; push m to 32 →
              ~9%. Target tokens/sec for 45% MFU: 0.45 × 256 × 990e12 / (6×70e9) ≈ 271k tok/s. The
              exact split isn't unique — the reasoning is what's graded.
            

          

        


        

          

            Local exercise
            Verify DP gradient equivalence in PyTorch
            
          

          

            On your machine (single GPU is fine, or gloo on CPU): show that averaging
            gradients across two "workers" each seeing half a batch equals the gradient of the full
            batch on one worker, to numerical tolerance. Then run it under
            torch.distributed with DistributedDataParallel and confirm the
            all-reduce does exactly this. Understanding why DP is gradient-averaging (and why
            you divide by world size) is a frequent probe.
