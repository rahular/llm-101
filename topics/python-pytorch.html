1. Shapes are the whole game

Ninety percent of live-coding bugs are shape bugs. Build the habit of narrating the shape of every tensor. A transformer activation is conventionally (batch, seqlen, d_model) — batch, sequence length, model dimension — and attention adds a heads axis to get (batch, n_heads, seqlen, head_dim). Train yourself to read an op and predict the output shape before running it.

⚠️ Gotcha: transpose semantics differ

            permute (or passing it three args) is a classic slip.
          

        


        
        
2. Broadcasting

        

          Broadcasting lets tensors of different shapes combine without explicit copies. The rule:
          align shapes on the right; for each axis, sizes must be equal, or one of
          them must be 1 (which is stretched). A missing leading axis is treated as 1.
        

        

          (batch, 1, d_model) + (1, seqlen, d_model) → (batch, seqlen, d_model) 

          (batch, seqlen, d_model) + (d_model,) → (batch, seqlen, d_model) 

          (batch, seqlen, d_model) + (seqlen,) → error (seqlen ≠ d_model on the last axis)

3. einsum: the shape calculator you should love

4. reshape vs view vs contiguous

        

          A tensor is a flat buffer plus strides that say how far to step per axis.
          reshape/view just reinterpret strides when possible — no data
          moves. transpose/permute only rearrange strides, so the result
          is non-contiguous: its memory order no longer matches its logical order.
        

        
    
          
  • view requires contiguous memory and errors on a transposed
            tensor; it only ever reinterprets strides, never copies.
    • 
          
  • reshape copies if needed, so it "just works" — at the cost of a hidden
            allocation. Hence the idiom x.transpose(1,2).contiguous().view(...): the
            .contiguous() forces a repacked copy so view is legal.
    • 
        


        

          

            See the strides move
            
            
            
          

          
          

        


        

          
Why this matters

          

            "Why does .view() throw after a transpose?" is a common warm-up.
            Answer in terms of strides and memory contiguity, then mention that
            reshape silently inserts the copy so it "just works" but can cost you a
            hidden allocation in a hot loop.

6. Softmax & cross-entropy from scratch

        

          Everyone should implement these at least once, because two things only click by doing:
          the max-subtraction trick for numerical stability, and that you compute
          cross-entropy directly from logits via log-softmax (never
          log(softmax(x)), which overflows/underflows). More on the numerics in
          Numerics & Precision.
        

        

          softmax(x)ᵢ = e^{xᵢ − m} / Σⱼ e^{xⱼ − m},   m = max(x). 

          logsumexp(x) = m + log Σⱼ e^{xⱼ − m}. 

          CE = logsumexp(x) − x_target.

7. The autograd mental model

        

          The cell below runs real autograd, but you must also be able to explain and
          hand-derive what it's doing. The model:
        

        
    
          
  • Every op on a tensor with requires_grad=True records a node in a
            dynamic computation graph (built on the forward pass).
    • 
          
  • loss.backward() walks that graph in reverse (reverse-mode autodiff),
            applying the chain rule to accumulate .grad on each leaf tensor.
    • 
          
  • Gradients accumulate (add) into .grad — this is why you
            call optimizer.zero_grad() each step, and also what makes gradient
            accumulation over micro-batches free.
    • 
          
  • torch.no_grad() / detach() stop graph tracking — used in
            eval, inference, and when you deliberately cut the gradient (e.g. target networks,
            straight-through estimators).
    • 
        


        

          To prove you understand it, derive the backward of a linear layer by hand: for
          y = xW with upstream gradient g = ∂L/∂y, you get
          ∂L/∂x = gWᵀ and ∂L/∂W = xᵀg. The cell below builds a 2-layer
          MLP, calls loss.backward(), and prints the gradients autograd produced —
          which are exactly those hand-derived expressions.

            Local exercise
            Write a full PyTorch training step from memory
            
          

          

            On your own machine (this needs real torch), write — without looking — a minimal
            training loop for a linear model: forward, F.cross_entropy,
            zero_grad, backward, step. Deliberately practice
            the ordering (zero_grad before or after step? why does it not
            matter as long as it's once per iteration?) and confirm the loss drops. This is the
            canonical "blank editor" exercise — every training script grows from this skeleton.
          

          

            Reference skeleton
            
import torch, torch.nn as nn, torch.nn.functional as F

model = nn.Linear(16, 10)
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)

for step in range(100):
    x = torch.randn(32, 16)
    y = torch.randint(0, 10, (32,))
    logits = model(x)                 # (32,10)
    loss = F.cross_entropy(logits, y) # log-softmax + NLL, fused & stable
    opt.zero_grad(set_to_none=True)   # clear accumulated grads
    loss.backward()                   # reverse-mode autodiff
    opt.step()                        # W -= lr * m̂/(√v̂+eps)
# zero_grad can go anywhere once per iter, as long as it's before the NEXT backward.
