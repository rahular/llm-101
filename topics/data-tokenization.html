Topic 10 · Data

Data & Tokenization

Data quality is the least-glamorous, highest-leverage lever in pre-training — recent frontier reports repeatedly credit mixture and filtering choices over architecture tweaks. This page covers the pipeline end to end, with runnable BPE, dedup, and packing, plus the multilingual story most treatments skip.

1. The pipeline

A pre-training data pipeline turns a raw crawl into packed token sequences. The stages, roughly in order:

StageWhat it doesFailure mode if skipped
ExtractionHTML → text (e.g. trafilatura), language IDBoilerplate, nav junk dominates
DedupExact + near-dup removal (MinHash/LSH)Memorization, wasted compute, eval leakage
Quality filteringHeuristics + model-based classifiersGarbage tokens dilute signal
Safety / PIIToxicity, PII redactionHarmful or private data memorized
DecontaminationRemove eval-set overlapInflated, meaningless benchmarks
TokenizationText → token IDs (BPE/SP)—
Packing / shardingConcatenate into fixed-length sequencesPadding waste, slow loaders
Why this matters

The signal here isn't reciting stages — it's judgment about ordering and cost. Dedup before quality-filtering (cheaper to filter less data). Decontaminate against your actual eval suite. Everything runs at petabyte scale, so each stage must be a streaming, embarrassingly-parallel job (Spark/Beam/Ray over sharded files) — see Infra & Tooling.

2. Tokenization: BPE from scratch

Byte-Pair Encoding starts from single characters/bytes and greedily merges the most frequent adjacent pair into a new token, repeating until it reaches the target vocab size. The learned merge list (ordered) is the tokenizer. Encoding a new string replays the merges in order. Implementing the training loop from scratch is a clean, common ask.

Key refinements over this toy version, and why they matter:

        
    
          
  • Byte-level BPE (GPT-2 onward): operate on the 256 raw bytes, not
            Unicode characters. Guarantees zero out-of-vocabulary — any string encodes —
            and handles emoji, code, and every script uniformly. The cost: multi-byte characters
            (most non-Latin scripts) take several tokens each.
    • 
          
  • SentencePiece (BPE or unigram): trains directly on raw text with no
            pre-tokenization, treats space as a normal symbol (▁), so it's language-agnostic — no
            reliance on whitespace word boundaries. Standard for multilingual and non-space-delimited
            languages.
    • 
          
  • Pre-tokenization regex: splits on whitespace/punctuation before BPE so
            merges don't cross word boundaries in unhelpful ways.
    • 
        


        

          
⚠️ The multilingual tokenizer tax

          

            A vocab tuned on English fragments other scripts into many more tokens per word (poorer
            "fertility"), so the same sentence costs more tokens → more compute, less effective
            context, and worse quality for that language. If you work on non-English models this is
            a first-order design decision: vocabulary allocation across languages, fertility
            measurement, and the quality/compute trade-off of a larger multilingual vocab all
            materially change what the model costs and how well it works.
          

        


        

          

            Discuss
            Vocab size trade-offs
            
          

          

            Be able to argue both directions: a larger vocab → shorter sequences (fewer
            tokens per doc, so more text per context and cheaper attention) but a bigger embedding
            /unembedding matrix and softmax, rarer tokens seen less often. A smaller vocab →
            cheaper output layer but longer sequences. Where does the optimum sit, and how does it
            shift for a multilingual model? What breaks if the vocab is 10× too large for your data?
          

        


        
        
3. Deduplication: MinHash + LSH

        

          Near-duplicate documents cause memorization, waste compute, and leak eval data. Exact
          dedup (hash the whole doc) misses near-dups. The standard scalable approach estimates
          pairwise Jaccard similarity of shingle sets with MinHash,
          then uses LSH to only compare likely-similar pairs instead of all N².
        

        

          MinHash fact: P( minhash_h(A) == minhash_h(B) ) = Jaccard(A, B). 

          Average agreement over k hashes → an unbiased Jaccard estimate.
        


        

          

            MinHash estimates Jaccard
            
            
            
          

          
          

        


        

          LSH makes this scale: split the signature into b bands of
          r rows, hash each band, and only treat docs sharing a full band as candidates.
          The band/row choice tunes the S-curve — the similarity threshold above which pairs are
          almost always caught. This turns an O(N²) all-pairs comparison into near-linear.
        


        
        
4. Quality filtering

        
    
          
  • Heuristics (cheap first pass): length bounds, symbol/word ratios,
            fraction of alphabetic chars, stopword presence, mean line length, repetition ratio.
            Gopher and C4 rules are the canonical references.
    • 
          
  • Model-based: a lightweight classifier scoring "is this like
            high-quality reference text?" (the classic trick: positives = Wikipedia/books,
            negatives = raw crawl). Modern pipelines increasingly use LLM-as-judge quality scores.
    • 
          
  • Perplexity filtering: score docs with a small reference LM and cut the
            extreme tails (both very high perplexity garbage and suspiciously low near-dups).
    • 
        

        

          
Why this matters

          

            The mature take: quality filtering is a precision/recall trade-off you can overshoot —
            too aggressive and you strip diversity and hurt the model. The frontier finding
            (repeated across recent tech reports) is that data quality and mixture often beat
            raw scale. Have an opinion on how you'd measure a filter's effect: small-scale
            ablations with matched compute, not vibes.
          

        


        
        
5. Sequence packing

        

          Documents have wildly varying lengths. Padding each to the max wastes compute on pad
          tokens. Packing concatenates tokenized documents (with a separator/EOS) and slices the
          stream into fixed-length training sequences, so nearly every token is real. The subtlety:
          a packed sequence contains multiple documents, so attention should not cross document
          boundaries — hence document/attention masks (or accepting minor cross-contamination, which
          many pipelines do for simplicity).

6. Data mixing & curriculum

        

          Pre-training data is a mixture of domains (web, code, books, math, multilingual,
          Q&A). The mixture weights are a first-class hyperparameter — often more impactful than
          architecture tweaks. Key concepts:
        

        
    
          
  • Domain weighting: upsample high-value, scarce domains (code, math);
            downsample the near-infinite low-quality web. Methods range from hand-tuned to learned
            (e.g. DoReMi optimizes weights with a small proxy model).
    • 
          
  • Epoching: how many times to repeat scarce high-quality data before
            repetition hurts. Repeating a few epochs is fine; heavy repetition causes memorization
            and diminishing returns.
    • 
          
  • Curriculum / annealing: many recipes shift the mixture over training —
            e.g. a final "cooldown" phase on especially high-quality data (a widely reported trick).
    •

7. Decontamination

        

          If eval-set text leaks into training, your benchmarks are meaningless. Decontamination
          removes (or flags) training documents overlapping with eval sets — typically via n-gram
          overlap or the same MinHash machinery used for dedup. Points to raise: it must run against
          your actual eval suite, overlap thresholds are a judgment call, and you should
          report contamination rates rather than assume zero.
