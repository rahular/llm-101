Topic 09 · Systems

Infra, K8s & Dev Tooling

The unglamorous glue that sets a team's velocity — on any serious training team, dev tooling is half the job. Working depth on orchestration and checkpointing, plus real opinions on reproducibility and iteration speed.

1. Orchestration & Kubernetes

A training job isn't one process — it's hundreds of ranks that must start together, discover each other, and share high-speed networking. Kubernetes (or Slurm) is the layer that places and babysits them. The concepts to hold:

  • Pod — the unit of scheduling; for training, typically one pod per node binding that node's 8 accelerators, with resource requests/limits declaring the GPUs it needs.
  • Job / indexed Job (or a training operator like Kubeflow's PyTorchJob) — runs a fixed set of pods to completion, each with a rank index for torch.distributed rendezvous.
  • Gang scheduling — the critical one. A distributed job needs all N pods running simultaneously; scheduling 60 of 64 leaves them idle (and deadlocks the collective) while holding expensive GPUs. Gang scheduling (coscheduling plugins, Volcano) enforces all-or-nothing placement.
  • Taints / tolerations & node pools — keep GPU nodes reserved for GPU work; schedule to the right accelerator type and topology (same rack/spine for fast links).
  • Restart policy — on a pod failure, the operator restarts the job (or the failed rank in elastic mode), which reloads the last checkpoint — the recovery path from Accelerators.
⚠️ Why gang scheduling is non-negotiable

Without it, two large jobs can each grab half the cluster, each wait forever for the other half, and burn GPU-hours doing nothing — a classic distributed deadlock. Naming this failure mode signals you've actually operated a cluster.

2. Checkpointing & state

Covered from the fault-tolerance angle in Accelerators; here the focus is correctness of resumption. A resumable checkpoint must contain everything that makes the run bit-reproducible from that point, not just the weights:

  • Model weights (sharded across ranks for large models).
  • Optimizer state — Adam's m and v; forgetting this restarts momentum and dents the loss curve.
  • LR scheduler / step count — so the schedule continues, not restarts.
  • RNG state (per rank) — dropout, data shuffling, init reproducibility.
  • Dataloader position — which shard/offset, so you don't re-train on seen data or skip unseen data.

3. Experiment infrastructure

        

          At any moment a research team is running dozens of experiments; the infra that keeps them
          comparable and reproducible is a force multiplier (or, done badly, a constant tax).
        

        
    
          
  • Tracking — log metrics, configs, code version, and artifacts per run
            (W&B, MLflow, or in-house). The non-negotiable: given a result, you can recover the
            exact config and commit that produced it.
    • 
          
  • Config management — one structured, version-controlled config per run
            (Hydra/OmegaConf style), diffable against the baseline, so an ablation is literally a
            one-line delta and nobody wonders "what was different?".
    • 
          
  • Reproducibility — pinned dependencies/containers, seeded RNG, recorded
            data version. Bit-for-bit repro is expensive (see determinism in
            Numerics); statistical repro (same curve within seed
            noise) is the usual bar.
    • 
          
  • Launch & monitor — one command from config to a scheduled multi-node
            job, with dashboards and automated alerting on divergence (loss spike, NaN, throughput
            drop) so a bad overnight run is caught in minutes, not at standup.
    • 
        


        
        
4. Dev tooling & iteration speed

        

          The highest-leverage engineers are the ones who make the whole team faster. The mindset: find the friction
          in the common loop and remove it. Concretely:
        

        
    
          
  • Profiling — the PyTorch profiler / Nsight / XLA profiler to find the real
            bottleneck (compute? comms? dataloader? launch overhead?) before optimizing. Optimizing the
            wrong thing is the most common waste; measure first (roofline on
            Accelerators).
    • 
          
  • Fast inner loop — tiny-model / tiny-data "smoke" configs that exercise the
            whole pipeline in minutes, so a code change is validated before a big launch. Catching a
            shape bug in 2 minutes vs 2 hours of queue is the entire ROI of tooling.
    • 
          
  • Shared abstractions — a clean internal training library so nobody
            re-implements checkpointing, parallelism wiring, or logging per project (and per-project
            bugs don't multiply).
    • 
          
  • Regression guards — automated throughput/MFU and loss-curve checks in CI
            so a "harmless" refactor that halves MFU or perturbs the loss is caught immediately.
    • 
        


        

          
Why this matters

          

            Tooling questions are really "how do you think about leverage?" Strong answers name a
            specific friction, quantify its cost (GPU-hours or engineer-hours), and propose the smallest
            change that removes it — then mention how you'd measure that it actually helped. "I'd add a
            5-minute smoke test that runs the full pipeline at toy scale, gated in CI, because most of
            our failed launches are shape/config bugs that a full run only surfaces after an hour of
            queue" is the shape of a great answer.
          

        


        

          

            Exercise
            What must a checkpoint contain to resume exactly?
            
          

          

            Enumerate every piece of state needed so that resuming from step k produces the
            same trajectory as never having stopped (within seed noise). For each, say what goes wrong if
            you omit it (e.g. drop optimizer state → momentum resets → visible loss bump; drop dataloader
            position → data re-consumption or gaps). This exact question comes up constantly.
