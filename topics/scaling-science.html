Topic 06 · Training science

Scaling Laws & Experiment Design

The science layer — how to predict, plan, and measure. This is where seniority shows: allocating a fixed compute budget correctly, designing clean ablations, and reading results honestly. This is the discipline that turns GPU-hours into knowledge.

1. The training-FLOPs identity: C ≈ 6ND

Everything starts here. Training a dense transformer costs about 6 FLOPs per parameter per token: 2 for the forward pass, 4 for the backward. So total compute C ≈ 6 · N · D for N parameters and D training tokens. This one identity lets you convert freely between model size, dataset size, and compute — the backbone of every planning question.

C ≈ 6 · N · D   (FLOPs)   →   given any two, solve the third.

2. Scaling laws: Kaplan → Chinchilla

        

          Loss falls as a power law in model size, data, and compute — remarkably
          smooth over many orders of magnitude. The practically important question is: given a fixed
          compute budget, how do you split it between a bigger model and more tokens?
        

        
    
          
  • Kaplan et al. (2020) concluded you should scale model size much faster
            than data — pushing toward large, relatively under-trained models.
    • 
          
  • Chinchilla (Hoffmann et al., 2022) corrected this: model size and
            tokens should scale roughly equally with compute. The compute-optimal ratio is
            about ~20 tokens per parameter. A 70B model wants ~1.4T tokens. Chinchilla
            (70B/1.4T) beat Gopher (280B/300B tokens) using the same compute.
    • 
        


        

          
⚠️ "Compute-optimal" ≠ "what you should ship"

          

            Chinchilla optimizes training compute for a target loss. But a deployed model is
            run for inference billions of times, so it's usually worth overtraining a smaller
            model well past 20 tok/param (Llama-style) — you pay more training compute to get
            a cheaper, faster model at inference. Naming this inference-aware nuance is a strong signal.

4. IsoFLOP analysis

        

          The clean way to find the compute-optimal point: fix a compute budget, train several
          models of different sizes (each for the token count that uses exactly that budget), and plot
          final loss vs model size. You get a U-shape — too small underfits, too big
          is under-trained on too few tokens — and the minimum is the optimal size for that budget.
          Repeat across budgets to trace the scaling law. This is the Chinchilla methodology.

5. Designing a clean experiment

        

          The recurring real-world scenario: "you want to know if X helps — how do you find out?" A
          rigorous answer covers:
        

        
    
          
  1. One variable. Change only X; hold architecture, data, tokens, LR
            schedule, and seed policy fixed.
    2. 
          
  2. Match compute, not just steps. If X changes FLOPs/step (e.g. a wider
            FFN), compare at equal total compute or equal wall-clock, not equal step count —
            otherwise you're just measuring "more compute helps."
    3. 
          
  3. Proxy scale + ladder. Test at several small sizes and check the effect
            trend holds as you scale; a win that shrinks with scale may vanish at target size.
    4. 
          
  4. Account for noise. Run multiple seeds; report the effect size relative
            to seed-to-seed variance. A 0.5% loss delta inside 1% seed noise is nothing.
    5. 
          
  5. Right metric. Loss for a clean signal, but confirm on downstream evals —
            they can diverge (next section).
    6.

6. Evaluation: loss vs benchmarks

        
    
          
  • Loss/perplexity is a smooth, low-noise signal ideal for scaling and
            ablations — but it measures next-token prediction, not capability.
    • 
          
  • Downstream benchmarks (MMLU, GSM8K, code) measure what you care about but
            are noisy, can be gamed, and often move in steps. Loss can drop while a benchmark stays
            flat then jumps — the "emergence" debate: some argue apparent emergence is an artifact of
            discontinuous/thresholded metrics rather than a true phase change.
    • 
          
  • Contamination silently inflates benchmarks — decontaminate against your
            eval suite (see Data & Tokenization) and report
            contamination rather than assume zero.
    • 
        


        

          
Why this matters

          

            "Your loss is dropping but MMLU is flat — what's happening?" Good answers: the metric may be
            thresholded (accuracy jumps only once the model crosses a capability bar), the eval may be
            noisy/small (widen it, add seeds), the capability may not be represented in the data mix, or
            the benchmark may be saturated/contaminated. The meta-point: never trust a single metric;
            triangulate loss + several evals + qualitative samples.
