Accelerators & Performance

The hardware you're optimizing for. Enough architecture to reason about whether a kernel is good, how interconnect constrains your parallelism plan, and how to design fault tolerance at a scale where hardware failure is routine.

1. The GPU memory hierarchy

Performance reasoning starts with the memory pyramid. Each level up is ~an order of magnitude faster and smaller. The entire game of GPU optimization is keeping data in the fast levels and minimizing trips to the slow ones.

LevelSize (A100)BandwidthRole
Registers~256 KB/SM~fastestper-thread scalars
Shared mem / L1 (SRAM)~192 KB/SM~19 TB/stile working set (FlashAttention lives here)
L2 cache~40 MB~several TB/scross-SM reuse
HBM (global)40–80 GB~2 TB/smodel, activations, everything
Host / NVLink / network—≤ ~0.9 TB/scross-device

Execution model: threads group into warps of 32 (lockstep SIMT); warps run on Streaming Multiprocessors (SMs); tensor cores do the bulk matmul FLOPs. Occupancy — how many warps are resident to hide memory latency — is a key tuning knob, but high occupancy alone doesn't guarantee speed.

2. Roofline: compute-bound vs memory-bound

The one model that answers "is this kernel any good?". Arithmetic intensity = FLOPs per byte moved from HBM. Compare it to the hardware's ridge point (peak FLOP/s ÷ bandwidth). Below the ridge you're memory-bound (starved for data); above it you're compute-bound (using the tensor cores well). Big dense matmuls are compute-bound; softmax, norms, elementwise ops, and naive attention are memory-bound — which is why fusion and FlashAttention (see Attention) matter.

attainable FLOP/s = min( peak_FLOP/s, arithmetic_intensity × bandwidth )

3. Interconnect — it dictates your parallelism plan

        

          Which parallelism goes where is a direct function of link bandwidth (revisit the mapping on
          Distributed Training). The hierarchy:

          The rule that falls out: put the highest-communication parallelism (TP, which syncs
          twice per layer) on the fastest link (NVLink, intra-node), and the
          lowest (DP, one all-reduce per step) on the slowest. Getting this backwards is a
          common wrong answer.
        


        
        
4. Non-NVIDIA accelerators: TPU & the compiler model

        

          Several frontier labs train primarily on TPUs (or AWS Trainium), so know the shape of it. A TPU is a
          systolic-array matmul engine with large MXUs, connected in a 2D/3D torus
          pod with very high-bandwidth inter-chip links (ICI) — designed for exactly
          the collective-heavy communication of training. The big conceptual shift is the
          compiler-centric model: you express computation in JAX/XLA, and
          XLA compiles the whole graph ahead of time — fusing ops, choosing layouts,
          and inserting collectives — rather than eager op-by-op execution. This means shapes must be
          static, and performance work is about helping the compiler (fusion, sharding annotations via
          GSPMD) rather than hand-writing kernels.
        

        

          
Why this matters

          

            "What changes moving from GPU/PyTorch-eager to TPU/JAX-XLA?" — static shapes (no
            data-dependent control flow without care), whole-program compilation and fusion, sharding
            expressed declaratively and lowered to collectives by the compiler, and a first
            compilation cost you pay once. The mental model flips from "I place and tune kernels" to "I
            shape the program so the compiler can."
          

        


        
        
5. Fault tolerance — failure as the steady state

        

          At thousands of accelerators, hardware failure is not an edge case — it's the steady state. If
          one chip fails every few years on average, a run with thousands of chips sees failures every
          few hours. Your training system must expect and absorb this.
        


        

          

            Failures are routine at scale
            
            
            
          

          
          

        


        
The toolkit, and the trade-offs to discuss:

        
    
          
  • Checkpointing — the backbone. Save weights + optimizer state + RNG +
            dataloader position often enough that a failure costs little recompute, but not so often that
            I/O dominates. Async checkpointing (copy to host, write in background) and
            sharded checkpointing (each rank writes its shard) hide the cost.
    • 
          
  • Optimal interval — the Young/Daly result: checkpoint every
            √(2 · checkpoint_time · MTBF) to minimize total wasted time. Too frequent wastes
            I/O; too rare wastes recompute after a crash.
    • 
          
  • Elastic / auto-restart — detect the dead node, reschedule (Kubernetes,
            see Infra & Tooling), reload the last checkpoint, and
            continue past the point of failure.
    • 
          
  • Stragglers — a slow (not dead) node bottlenecks every collective; detect
            via per-step timing outliers and evict.
    •
